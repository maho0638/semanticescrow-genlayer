# SemanticEscrow — Phase 3 Studio consensus acceptance criteria

## Test target, not a success claim

This stage runs on a **disposable GitHub-hosted local Studio v0.123.0-rc.7** with chain ID 61127 and exactly **five registered validator identities**. The official pinned Compose manifest is in `.ci/studio-v123-compose.yml`. Each validator uses a deterministic *mocked* web/LLM backend: this is a **real Studio consensus/GenVM integration run**, not evidence of five external independent AI providers or authentic publishers.

The test uses transient accounts generated by the GenLayer test harness and **local simulated GEN only**. The private keys must not be logged, exported, stored in GitHub files or disclosed to the user. It must not touch any real GEN wallet or Portal account.

The acceptance criteria are deliberately stricter than source compilation:

1. JSON-RPC and SDK chain IDs exactly equal 61127; `sim_countValidators` == 5.
2. Contract deploys in real local GenVM, with wait target `finalized`; reading `deal_count` succeeds.
3. Two-account scenario signs transactions with distinct local buyer/seller accounts; native GEN deposit exactly equals the milestone sum; return receipt indicates successful execution (not merely network acceptance).
4. Consensus voting map has five distinct registered validator identities; majority has at least 3 `agree`. `idle` due to mathematically early quorum is **not** independently counted as an agreeing vote. Only full vote/receipt data may justify a pass.
5. The payable deal, first active milestone, future waiting milestone and sum-conserving ledger read back after finality.
6. The authorized seller submits 2 hash-committed mocked HTTPS bodies in a finalized Studio write; the manifest and `SUBMITTED` state read back.
7. Five Studio validators rerun source verification and frozen-rubric evaluation with identical mocked inputs. `assess` yields a finalized, execution-successful `APPROVED` business verdict with `APPROVE_PENDING` state, exactly two `VERIFIED` source digests, and **no early GEN release**.
8. If any stage has not been verified, report **BLOCKED / PARTIAL**, not full completion. Do not substitute GLSim or Direct Mode for Studio, nor substitute an `Accepted` receipt for `Finalized`.

## Non-goals, not evidence of funds safety

- Real external EVM recipient **credit** is unavailable as proof from local Studio: its Ghost contract layer is not implemented. `PAYOUT_QUEUED` is an intent state, never a recipient balance receipt.
- Real DNS resolution, redirect/publisher authenticity and malicious-source protections, validator LLM robustness, adverse transfer recovery, Studio Dev/public Bradbury signed publish, real GEN wallet use, external security audit and Portal submission are not verified here.
- Later release/security gates remain independent, even if this Stage-3 consensus integration succeeds.
- No main-branch merge, public deploy, user-wallet signature or Portal submission is allowed by this local QA workflow.
